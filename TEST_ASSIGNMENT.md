# Задание: Асинхронный сервис процессинга платежей

## Описание

Необходимо реализовать микросервис для асинхронной обработки платежей. Сервис принимает запросы на оплату, обрабатывает их через внешний платежный шлюз (эмуляцию) и уведомляет клиента о результате через webhook.

## Сущности

### Платеж (`Payment`)

1. ID платежа (уникальный идентификатор)
2. Сумма (`decimal`)
3. Валюта (`RUB`, `USD`, `EUR`)
4. Описание (строка)
5. Метаданные (JSON-поле для дополнительной информации)
6. Статус (`pending`, `succeeded`, `failed`)
7. Idempotency key (уникальный ключ для защиты от дублей)
8. Webhook URL (для уведомления о результате)
9. Даты создания и обработки

## Функционал API

### 1. Создание платежа

```http
POST /api/v1/payments
```

#### Параметры запроса

- Заголовок: `Idempotency-Key` (обязательный)
- Тело запроса:
  - сумма
  - валюта
  - описание
  - метаданные
  - webhook_url

#### Ответ

- Код: `202 Accepted`
- Тело:
  - `payment_id`
  - статус
  - `created_at`

### 2. Получение информации о платеже

```http
GET /api/v1/payments/{payment_id}
```

#### Ответ

- Детальная информация о платеже

## Технические требования

### Брокер сообщений

- При создании платежа публикуется событие в очередь `payments.new`.
- Один consumer:
  - получает сообщение из очереди;
  - эмулирует обработку платежа (2–5 секунд, 90% успех, 10% ошибка);
  - обновляет статус в БД;
  - отправляет webhook-уведомление на указанный URL;
  - реализует повторные попытки при ошибках отправки.

### Гарантии доставки

- Outbox pattern для гарантированной публикации событий.
- Idempotency key для защиты от дублей.
- Dead Letter Queue для сообщений, не обработанных после 3 попыток.

### Аутентификация

- Статический API-ключ в заголовке для всех эндпоинтов.

### Стек технологий

- FastAPI + Pydantic v2
- SQLAlchemy 2.0 (асинхронный режим)
- PostgreSQL
- RabbitMQ (FastStream)
- Alembic (миграции)
- Docker + docker-compose

## Требования к результату

1. Модели и миграции: таблицы `payments` и `outbox`.
2. API-эндпоинты: создание и получение платежа.
3. Consumer: один обработчик, выполняющий весь процесс.
4. Outbox pattern: гарантированная доставка событий.
5. Retry: 3 попытки с экспоненциальной задержкой.
6. Dead Letter Queue: для окончательно упавших сообщений.
7. Docker: compose-файл с сервисами `postgres`, `rabbitmq`, `api`, `consumer`.
8. Документация: README с инструкцией по запуску и примерами.

## Критерии оценки

1. Архитектура и чистота кода.
2. Корректная реализация Outbox pattern.
3. Работа с RabbitMQ (очереди, обменники, DLQ).
4. Идемпотентность.
5. Обработка ошибок и retry-логика.
6. Работоспособность Docker-окружения.
